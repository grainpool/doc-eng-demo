# ARCHITECTURE.md — the reconciliation model

Concord treats documentation as a projection of product truth. The pipeline is a sequence of pure
stages (all in `packages/concord-core`, no I/O) driven by a Worker executor
(`packages/concord-api/src/run.ts`). This document explains the model; the code is the authority on
detail.

## The fact graph

**Facts** are keyed claims about the product (`limit.upload.csv.max_bytes`,
`availability.feature.analysis_sessions.platform.ios`, `term.canonical.task`,
`retention.artifact.days`, …). **Projections** are places in the documentation where a fact is
rendered. A run snapshots the facts, parses the estate into **doc units**, extracts projections,
compares, and acts.

## Six source tiers — why truth is deliberately scattered

Product truth originates from six *structurally different* places, because that is what makes
arbitration a real problem rather than template rendering (anti-pattern AP1: "one magical YAML"
would make Concord trivial and dishonest):

| Tier | Source | Example fact |
|---|---|---|
| T1_SCHEMA | Zod schemas / typed constants in `@relay/contracts` | upload size limit |
| T2_INTERFACE | CLI introspection JSON (generated by the CLI build) | command flags, exit codes |
| T3_CONFIG | `product-config.ts` (availability, retention, flags) | iOS availability |
| T4_RELEASE | dated release records (`product-truth/releases/`) | "iOS support ships in 3.1" |
| T5_DECISION | decision documents (`product-truth/decisions/`) | "keep the regression flag" |
| T6_COPY | the in-product copy registry (estate) | UI strings quoting limits |

**Authority arbitration**: when tiers disagree about a fact, a fixed authority order per fact family
decides which claim wins; the losing claim becomes a *conflict*, not a silent overwrite. A release
(T4) claiming something config (T3) contradicts is exactly the "announced but not shipped" case —
surfaced, attributed to an owner, never auto-resolved. Two competing T5 decisions about the same
flag produce a standing conflict that blocks patching of that fact until a human resolves it.

## Extraction — seven extractors, honest confidence

Each extractor projects facts from doc-unit bodies with a confidence reflecting its mechanism:

- `declared_reference` (1.0) — an explicit `concord:fact key=…` marker or `references_facts`
  frontmatter. Declared, not inferred.
- `frontmatter_field` (1.0), `generated_marker` (1.0) — structural declarations.
- `term_occurrence` (0.9) — canonical-term usage (changelog/release quotes exempted: history is
  allowed to quote old names).
- `availability_table` (0.9) — platform matrix cells.
- `numeric_pattern` (0.85) — "10 MB", "30 days" near a fact's vocabulary.
- `model_extraction` (≤ 0.7, hard cap) — a model reads prose the mechanical extractors cannot;
  its claims are *candidates* that must survive normalized-value comparison and falsification. The
  cap encodes that model perception is never as trustworthy as a declared marker.

Comparison is **normalized-value only** (AP2): "10 MB", "10240 KB", and `10485760` are the same
claim; textual uniformity is explicitly not the goal. Unknown units downgrade to `derived_prose`
rather than guessing.

## Classification — six rules, one temptation

Every (fact delta × projection) pair is classified by six ordered rules into an action class:

| Action | When | Who acts |
|---|---|---|
| `DETERMINISTIC_REGEN` | the rendering is mechanical (marker/table/generated page) | no model — regenerate/substitute |
| `GROUNDED_PATCH` | prose must change and evidence fully determines the change | model proposes, gates validate, human reviews |
| `EDITORIAL_REVIEW` | meaning/structure/judgment involved (procedures, claims, IA) | human, with a model draft at most |
| `UNRESOLVED_CONFLICT` | authoritative sources disagree, or evidence cannot resolve | human, with the conflict record |
| `NO_ACTION` | projection already agrees (or exempt register) | nobody |
| escalation via rule 6 | a decision fact or competing decisions touch the key | owner named in the record |

Conflicts **block** patching by fact key: a run will regenerate an availability matrix cell it is
sure about while refusing to touch prose about a fact two decisions are fighting over.

## Why escalation is a success

The failure mode this system is built against is the confident wrong edit. An escalation with an
owner, the competing claims, and a suggested question is the *correct output* whenever evidence
under-determines the change — it converts silent drift into a routed decision. The eval treats
expected escalations as hits and unsafe autofixes as a hard-gate failure (count must be 0), which is
the priority order the whole design encodes: precision over recall, honesty over coverage.

## Validation — mechanical gates, not prompt promises

Model-authored patches pass four gates in `patch-validate.ts` (invariant I6: "the prompt says not to
invent facts" is not a control):

1. **Evidence resolution** — every cited (fact_key, locator) must resolve in the current snapshot.
2. **Anti-hallucination extraction** — the extractors re-run over the *proposed* body; any fact key
   asserted that is not in the evidence set (and was not already asserted by the original body)
   rejects the patch.
3. **Register** — structure/meaning risk forces the editorial path.
4. **Path allowlist** — the target path (from the DocUnit, never the model) must be allowlisted;
   the denylist is checked first.

Surviving non-deterministic findings then face an **adversarial falsifier**: a separate model call
with no shared context whose job is to refute the finding, defaulting to *refuted under
uncertainty*. Suppressed findings are stored with their refutation text — visible, never deleted.

## Runs, replay, and the Change Lab

A run is a durable record (D1): snapshot, units, projections, impacts, patches, conflicts, findings,
steps, spend. The public demo replays five recorded real runs through the same renderer as live
runs (`changelab-render.js` — ONE renderer, one `ChangeLabRun` shape). The Access-gated Change Lab
applies one of two allowlisted mutation kinds (nine closed-value fact keys, or a doc-body edit on
ten editable units) to a **working copy**, runs the real pipeline, and — since Phase 19 — lands the
validated patches as a GitHub PR with the evidence in the body.

## Spend and safety rails

Model calls: ≤ 5 concurrent (bounded fan-out), ≤ 20 per run, ≤ $5 per UTC day, slot reserved before
each call, every call recorded as a `model_call` row with token counts and a prompt *hash*. Public
paths get a null model client — zero calls by construction (I11). On cap exhaustion a run ends
`partial` with `budget_exhausted` and unresolved impacts stay visible; nothing silently truncates.
