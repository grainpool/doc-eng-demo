PHASE 19 — GITHUB APP: ephemeral branch and pull request, under four independent restrictions.

Phase 18 is complete and verified: Access-gated live runs, verified JWTs, mutation allowlists, audit log.

Land patches as a real pull request. Read `security.md` §1, §4.3, and §8 before starting. This is the phase where a
mistake has consequences outside the demo, so the restrictions are layered deliberately — each one must hold on its own.

OPERATOR GATE — GITHUB. Two separate things here are MINE, and they are easy to conflate. Both must be done before this
phase can be verified, and you can do neither:

  (a) CREATING AND INSTALLING THE APP. I create it under `grainpool` with exactly three permissions (Contents: write,
      Pull requests: write, Metadata: read), install it on the estate repo and nowhere else, and download the private
      key. I then supply you the App id, the installation id, and the key.
      If you do not have all three, STOP and ask me for them by name. Do NOT proceed with a personal access token as a
      substitute — a PAT is account-scoped and long-lived, and it defeats three of the four layers below at once. Do not
      write the publish path against placeholder credentials to "wire it up now and fill them in later"; an untested
      GitHub write path is the one thing in this project that can do damage outside the demo.

  (b) BRANCH PROTECTION ON `main` OF THE ESTATE REPO — require a PR before merging, block force pushes, block branch
      deletion. This is a REPOSITORY SETTING I configure in GitHub's UI. The App does not grant it, installing the App
      does not create it, and your credentials cannot set it. It is a distinct step from (a) and I will tell you when it
      is in place.
      Why it is load-bearing: the App holds `Contents: write`. Without branch protection that permission can commit
      straight to `main` — an AI-proposed patch, triggered by a visitor, landing on the published docs site with no
      human in the loop. Branch protection is what forces the token down the PR path.
      Your job is to VERIFY it, not assume it: attempt a direct push to `main` with the installation token and confirm
      it is rejected. If it succeeds, that is a finding — stop and tell me, because the layer is missing. Report the
      observed rejection, and document in `SECURITY.md` that this layer is operator-configured and therefore worth
      re-checking rather than assumed.

LAYER ZERO, before anything else: the App is installed on the **estate repo (repo 2)** and nowhere else. Repo 1 — all
code, all CI, all product truth — has no installation and is therefore unreachable, not merely disallowed. Everything
below is defence in depth inside repo 2. Never propose a second installation, and never route a repo-1 change through
another mechanism; if a run concludes something in repo 1 should change, the correct output is an escalation naming the
owner (`constraints.md` §G21).

SCOPE

1. The GitHub App — I CREATE AND INSTALL IT (gate (a) above); your deliverable is the documentation of it in
   `SECURITY.md`, written so a reader could reproduce the configuration and see why each choice is deliberate:
   - permissions: **Contents: write, Pull requests: write, Metadata: read**. Nothing else. `Pull requests: write` alone
     cannot create a branch, which is why Contents:write is required — say so in the doc so the scope looks deliberate
     rather than lazy.
   - installed on **the estate repo only**.
   - the estate repo contains **no `.github/` directory at all**. All CI lives in repo 1, where this App is not
     installed — so there is no privileged workflow within reach of a visitor-authored branch. State this as the
     structural argument it is, rather than relying on GitHub's workflow-trigger semantics.
     Note that Mintlify's GitHub app is also installed on repo 2 (Phase 11). Address that directly rather than leaving
     a reader to wonder: the argument is a property of the repo's *contents*, not of how many apps are installed, and
     Concord's App remains the only installation on repo 2 with `Contents: write`.
   - branch protection on `main`: PR required, no force push, no deletion. **Operator-configured** — gate (b) above.
     Mark it as such in the doc, and record the observed result of your direct-push attempt next to it. A control
     nobody can verify is a control nobody should trust.

2. Token handling — mint an installation access token PER RUN, scoped with `repositories`/`repository_ids` to that one
   repo, short-lived. Never return it in a response. Never log it. Never cache it beyond the run.

3. Path enforcement — TWO independent checks, both must pass:
   - in `concord-core` (pure, unit-tested): the DENYLIST is evaluated FIRST and independently, then the allowlist. A bug
     in the allowlist must not open a hole. Allowed globs and the denylist are exactly as in `security.md` §4.3.
   - in `concord-api`, immediately before the Octokit call, re-check every path in the commit.
   Normalize and reject traversal variants: `..`, URL-encoded `%2e%2e%2f`, absolute paths, backslashes, unicode
   normalization tricks, and symlink-looking names.

4. Publish step — branch `concord/run-{run_id}` (never visitor-controlled text): create branch → commit the allowlisted
   diffs → open the PR. All paths sent to the API are ESTATE-RELATIVE; the `estate/` mount prefix must never appear.
   PR body lists the fact deltas, the evidence for each patch, which impacts were escalated rather than patched, the
   estate SHA the run was built against, and a link to the public run inspector. Never interpolate model output into the
   branch name or PR title. On ANY failure after branch creation, DELETE the branch — no orphan refs.
   If the estate has moved ahead of the run's SHA the PR may conflict; that is ordinary git behavior and the honest
   outcome. Do not build a merge strategy for it.

5. Failure isolation — a GitHub failure must not fail the run. The run still completes; the `publish` step is marked
   failed and the patch bodies remain in R2. Record the PR url (or the failure) in `audit_log`.

6. Cleanup — a cron-triggered Worker that closes PRs and deletes `concord/run-*` branches older than 48 hours. Make it
   idempotent and safe to run repeatedly.

TESTS (required)
- `concord-core/test/path-allowlist.test.ts`: denylist wins over allowlist; each traversal variant rejected individually;
  `.github/**` rejected; `.ts`/`.py`/`.sql`/`.yaml`/`Dockerfile`/`package.json`/lockfiles/dotfiles rejected; only
  `.md`/`.mdx`/`.json` under the six allowed globs pass; any path resolving outside the estate repo rejected
  (invariant I16). Include a case where a path is in BOTH lists and assert the denylist wins.
- A test that an attempted write outside the allowlist is refused BEFORE any GitHub API call (spy on the client and
  assert zero invocations).
- `concord-api/test/github-cleanup.test.ts`: a failure injected after branch creation results in branch deletion.
- A test that no response body or log line contains the installation token or the private key.

HARD RULES
- Four independent layers, all required: least-privilege App on one repo; per-run repo-scoped token; branch protection
  forcing the PR path; path allowlist/denylist checked twice. Do not drop one because another covers it.
- A visitor-authored branch must not be able to introduce or trigger privileged CI. The absence of a workflows directory
  plus the `.github/**` denylist plus branch protection is what guarantees that.
- No GitHub credential ever reaches the client, a log, an error body, or a health check.
- Do not extend the path allowlist to make a scenario work. If a patch targets a non-allowlisted path, that patch should
  be refused and reported.

DONE WHEN
A live privileged run opens a real PR touching only allowlisted paths, with evidence in the body and a link to the run
inspector; every path-rejection test passes with zero GitHub calls; an injected mid-flow failure leaves no orphan branch;
the cleanup cron reaps; `main` cannot be pushed to directly.

Report: the PR url and its body verbatim; the path-rejection cases you verified; the observed cleanup behavior; and the
observed result of the direct-push-to-`main` attempt, naming branch protection as the operator-configured layer it is.
